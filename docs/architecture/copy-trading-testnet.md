# Binance 公共带单员 Testnet 跟单子系统

## 当前运行边界

- 数据源：Binance 网页使用的公开合约跟单 BAPI，只读取公开带单员榜单与操作历史。
- 执行端：当前只启用 Binance USD-M Futures Testnet。正式盘执行入口已经预留，但必须同时通过独立数据库、独立凭据、短时效激活文件、API Key 指纹、生产端点和零暴露门禁；本机尚无正式盘凭据，因此保持锁定。
- 账户模式：Hedge Mode。每个带单员由独立虚拟仓位账本归属，交易所只保存同币种、同方向的聚合仓位。
- 资金边界：逻辑操作额度 150 USDT，其中所有带单员共享的开仓保证金额度可由 Telegram 授权用户在 5–120 USDT 内配置，默认 120 USDT；交易账户实际可用余额保留线固定为 30 USDT，已实现/未实现盈亏不从共享额度重复扣减。每单保证金最多 5 USDT，不设置同币种累计保证金上限。线路权重不形成闲置资金硬隔离，带单员个人倍数只影响其未来目标名义金额；杠杆取交易所最新阶梯允许的最大值，仍不足时才按剩余额度缩量。降低额度不会调整或强平已有仓位和待入场单；已有占用超过新额度时，后续新开仓剩余额度为零，直到占用释放。
- 未公开持仓：不推断。首次纳入时只建立操作历史基线，不回放旧订单；此后只根据新增、可明确解释的 LONG/SHORT 成交增量行动。
- `positionSide=BOTH`：只归档，不生成交易信号。
- 访问受限：记录 `ACCESS_DENIED` 并暂停新开仓；不绕过验证码、WAF 或伪造浏览器指纹。

## 信号解释

- `LONG + BUY`、`SHORT + SELL`：增加对应带单员的虚拟仓位。
- `LONG + SELL`、`SHORT + BUY`：按该带单员当前虚拟仓位比例减仓，最多减到其自有虚拟数量。
- 开仓和加仓使用带单员公开成交均价作为最差保护价并提交交易所原生 `GTC` 限价。当前盘口
  更优时，该限价可立即按盘口或更优价格撮合；当前盘口更差时持续挂在带单员价格，不追价。
- 长线、短线和自定义槽位都没有钟表到期时间。待入场单持续存在，直到成交、用户/系统控制撤单、
  带单员退出该币种方向，或交易所明确拒绝/外部撤销。
- 带单员部分减仓不会把仍有效的待入场单误判为超时失败；带单员完全退出该币种方向时，先撤销
  仍可能成交的开仓/加仓单，终态部分成交先按实际成交量归属，再以市价清掉该带单员在系统中
  实际记录的全部剩余仓位。无法确认撤单结果时暂停该平仓信号并按原订单号重查。
- 减仓和平仓使用市价单立即同步风险敞口，不因等待更优价格继续持有带单员已经退出的仓位。
- 本地没有归属仓位的减仓/平仓：记为 `IGNORED_ORPHAN`，不会错误影响其他带单员。
- 自动槽位轮换先检查旧带单员的虚拟仓位和未决入场单：没有敞口就立即替换；有敞口时长线最多等待 1 天、短线最多等待 2 小时。期限内清仓后才替换，超时仍有敞口则取消本轮替换，绝不为换人强平。
- 自动选人要求候选当前至少有 200 名真实跟单者，并在候选通过回撤、样本、盈亏质量和活跃度硬门槛后，将跟单人数作为第一排序依据。边际递减的市场认可度在长线、短线 1、短线 2 的综合分中均占 35%，约 600 名当前跟单者达到该项满分；同一跟单人数档位再比较胜率、平仓表现、回撤、盈利集中度、活跃度、币种兼容率和操作新鲜度。长线、两个短线和七个自定义槽位全局禁止使用同一带单员，锁定槽位的备选也不能指向其他条线现任。带单员额度已满不是拒绝理由。两个短线槽位禁止互换已有带单员，避免槽位归属混乱。一个仓位从开仓、加仓到平仓始终归属开仓时的槽位。
- 自定义 1–7 完全由 Telegram 授权用户输入公开带单员 ID 或名称设置；每日短线和每周长线自动选人都不会候选、替换或清空这七个槽位。自定义槽位仍使用独立虚拟账本、相同的 10 秒轮询、共享资金上限、倍数配置、成交和盈亏通知。
- 已持久化的错误槽位归属不修改原始盈亏事件，而是追加带原因和操作者的纠正事件；估值、仓位展示和后续成交统一读取纠正后的有效槽位。
- 长线/短线权重只描述选人和归属优先级，不是保证金硬分区；所有带单员共享当前配置的开仓保证金额度（默认/最高 120U），
  同时受每单 5U 和 30U 备用金约束，不设置同币种累计上限。`DRAINING` 带单员不再增加风险。
- Testnet 压测阶段，日内综合候选必须达到 1/3/7 天至少 1/5/14 次操作、7 天至少 3 个活跃日；短线 1 先验证样本规模、回撤、盈亏比和盈利集中度，再从稳健候选中选择可信胜率最高者；短线 2 在相同风控基础上综合近期盈亏与活跃度，操作次数不再拥有最高优先级。
- 每次入场的目标名义金额为“该次带单员公开成交数量 × 公开成交均价 × 该带单员倍数”；倍数
  默认 1、只绑定带单员 ID。目标超过本地能力时，按“单笔最多 5U 保证金 × 该币种交易所允许
  的最大杠杆”和共享剩余保证金截断；仅当目标低于交易所最小下单金额时才提升到交易所最低值。
- 减仓比例使用完整公开操作推导出的带单员源仓位作为分母，不因某次本地限价尚未成交而漏算；
  最终平仓数量以系统账本中该带单员、币种、方向的实际剩余数量为准，避免残留或误平其他带单员。
- 每 10 秒估值同时执行“带单员 + 币种”级止损：把该带单员在同一币种当前仍持有的多仓、
  空仓分别按“本轮仓位已实现盈亏 + 当前未实现盈亏”计算后相加；例如多仓 `-15U`、
  空仓 `+10U` 时净值为 `-5U`，不会触发。合计达到 `-10U` 时，系统撤销该带单员在该币种
  的全部待入场单，并分别以市价平掉其多、空虚拟仓位。交易所共享仓位只按这套归属数量减仓，
  不会动其他带单员的同币种仓位。
- “当前仍持有”以该方向最新归属数量大于零为准，口径与 Telegram 仓位卡片的“累计盈亏”
  一致：仍未完全平掉的仓位会保留本轮部分减仓已实现盈亏并叠加当前未实现盈亏；已经完全平仓
  的旧交易不参与后续止损。因而某笔现有仓位虽然当前浮亏，只要该仓位累计仍盈利，就不会触发。
- 止损触发事件、触发估值、多空明细和每个归属平仓信号均为不可修改的数据库事实。触发后仅
  “该带单员 + 该币种”的开仓/加仓冷却 48 小时，减仓/平仓、其他币种及其他带单员继续正常
  执行。冷却跨重启生效；若旧限价在撤单竞争窗口内晚成交，下一轮会从新的归属仓位事件继续
  生成平仓信号，直至该范围归零。
- 交易所同一币种同一方向的数量必须等于所有带单员虚拟数量之和；不一致时巡检暂停新开仓并通知。

## 盈亏口径

- 系统总盈亏以专用 Binance USD-M Testnet 账户相对首次系统基线的余额变化为准；累计值包含
  手续费、资金费与未实现盈亏。每 10 秒保存一次不可修改的账户估值，可按上海自然日和自然月
  计算“今日/本月/累计”。
- 各带单员盈亏只使用本系统真实成交回报、该带单员独立虚拟仓位的加权开仓均价，以及交易所
  当前标记价计算。该值是归属毛盈亏，不重复猜测 Binance 网页未公开仓位，也不把网页展示的
  带单员收益当作本系统收益。
- 每笔实际成交同时绑定当时的固定槽位。长线、短线 1、短线 2、自定义 1–7 的
  今日/月度/累计毛盈亏都按线路连续保存；换人不会清零该线历史表现，个人盈亏明细仍按
  带单员独立保留。
- 手续费和资金费只在系统总盈亏中权威体现，不强行按带单员拆分；因此各带单员毛盈亏之和与
  系统净盈亏允许存在合理差额。
- 用户要求恢复初始资金时，系统在同一事务中追加不可修改的资金基线与盈亏统计基线，
  不删除历史成交、估值或审计记录。重置时交易净值从 150 U 重新计算，之后按
  “150 U + 基线后新盈亏”变化；已有仓位仍占用保证金，未平仓位会随行情立即产生新浮动盈亏。

## 幂等与异常状态

每个公开成交增量、信号、提交声明和交易所 `newClientOrderId` 都由稳定摘要派生。提交声明
必须先写数据库再调用交易所，并持久化订单类型、保护价格和可空的到期时间。网络结果不确定时只按
同一个客户端订单 ID 查询，不盲目重下。尚未成交的保护限价也计入 150U 额度占用，避免多个
加仓挂单并发成交后突破资金边界。

账户预警线只暂停新开仓，带单员减仓和平仓继续允许；紧急线进入 `REDUCE_ALL`。安全原因触发的全部减仓在虚拟仓位、交易所仓位、系统挂单和未决恢复信号全部归零后仍回到 `PAUSED_NEW_ENTRIES`；只有授权 Telegram 用户主动发起的人工清仓才在同样的四重确认后自动恢复。

资金分配不再把长线/短线槽位权重当作不可借用的保证金硬分区。每笔新单保证金上限为 5 USDT，不设置同币种累计保证金上限，所有带单员共享当前配置的 5–120 USDT 开仓额度（默认 120 USDT）；逻辑净值中的盈亏只展示一次，不再重复缩减该额度，交易账户实际可用余额仍保留 30 USDT 底线。目标名义金额优先匹配带单员，杠杆固定选择最新 `leverageBracket` 对当前币种允许的最高初始杠杆（协议边界 125 倍）。杠杆不改变按成交名义金额收取的交易手续费；入场继续使用可立即成交的保护限价，避免为追求 maker 费率而扩大跟单时差。

| 任务 | 周期 | 作用 |
| --- | --- | --- |
| `aiq-copy-poller.service` | 10 秒循环 | 分带单员采集、归一化、Testnet 下单、账户/带单员估值与通知 |
| `aiq-copy-leader-selector.timer` | 上海时间每日 00:00 | 短线 1 最高胜率；短线 2 当日日内综合最优 |
| `aiq-copy-long-leader-selector.timer` | 上海时间每周日 00:00 | 综合收益、回撤、稳定性、历史长度与可跟随性选择长线 |
| `aiq-copy-watchdog.timer` | 每 30 分钟 | 确定性检查数据库、轮询、风险、死信和仓位对账 |
| `aiq-copy-codex-audit.timer` | 每小时 | 用脱敏摘要做结构化审查，仅执行本地白名单动作 |
| `aiq-copy-telegram.service` | 持续长轮询 | 状态面板、通知、槽位增删改以及二次确认控制 |

自动选人会逐行校验 ROI、胜率和回撤榜候选；单个缺失名称或字段异常的公开条目只记录脱敏
跳过证据，不会中断整轮选择。若所有榜单都没有结构有效的候选则保留现有人选并失败告警。
选人失败会重启只读 Codex 审查，使上海 00:00 同时启动的小时审查重新读取失败记录，避免
systemd 合并启动请求后漏诊刚发生的选人故障。

Telegram 的底部键盘只保留六个高频入口，使用 `is_persistent=false` 允许用户收起键盘，
同时使用 `one_time_keyboard=false` 防止选择入口后自动丢弃键盘状态，使导航继续保留在
输入框旁的原生小键盘图标后面。该图标最终仍由 Telegram 客户端控制，服务同时为默认范围
和每个授权私聊配置并回读验证常驻 Bot
命令菜单，第一项 `/menu` 可重新下发导航键盘。其中“盈亏”展示系统今日、本月和累计净盈亏，
同时展示长线、短线 1、短线 2、自定义 1–7 跨换人的归属盈亏，下方再按槽位和“排空仓位”
的顺序提供各带单员明细按钮。所有出现带单员 ID 的 Telegram 仓位、订单、通知、确认和结果
消息都同时显示最新公开名称。进入“带单员”后，通过独立内嵌管理面板选择
长线/短线槽位、查看带有近期操作证据的候选，或直接为“自定义 1–7”输入任意可验证的公开带单员 ID/名称并替换、删除。管理页正文以 1–10 标示所有槽位，内嵌键盘使用两行紧凑编号；点击编号后才展示该槽位的设置、候选和清空操作。自定义槽位不受自动选人的胜率、活跃度和 Testnet 币种兼容筛选门槛约束，但实际出现 Testnet 不支持的币种时仍按执行规则安全跳过。所有写操作均须由授权用户
二次确认，确认令牌两分钟失效且只能消费一次。新增带单员先建基线，不回放历史订单。
手动输入 ID 或 Binance 链接时，只要公开身份有效即可建立确认，不再因历史订单的多空方向
证据不完整拒绝整个带单员；首次轮询直接把这部分历史记录作为基线。后续新操作仍必须逐笔
解析出明确的 LONG/SHORT 才会生成下单信号，系统不会把不明确记录猜成某个方向。
管理面板另提供“配置跟单倍数”：范围 1–10 倍，配置绑定带单员 ID 而非槽位。自动或手动换人后，
旧人的倍数不会传给新带单员，新人无历史配置时为 1 倍。倍数只参与后续新信号的本地比例目标计算；
已有仓位和已持久化的待入场订单保持原数量，减仓继续按各带单员自己的虚拟仓位比例执行。
“资金边界”页另提供“配置可用保证金”：可快捷选择 30/60/90/120 U，或输入 5–120 U 的自定义额度。修改必须二次确认并写入不可修改的审计事件，仅影响后续新开仓；已有仓位和待入场订单不改量、不撤单也不强平。
每个槽位的候选页把推荐点选和“输入链接 / ID / 名称”合并为一个入口：用户可以直接粘贴
`https://www.binance.com/<locale>/copy-trading/lead-details/<ID>?timeRange=30D` 形式的 Binance
带单员详情链接；服务只从严格校验过的 `www.binance.com` HTTPS 路径中提取 ID，不访问用户提供的任意 URL。
纯 ID 和链接都会先从 AUM、胜率、回撤榜首屏快速定位，再用完整 ROI 公开目录兜底并刷新最近 30 条操作；
回复名称时按名称搜索并返回唯一 ID 按钮。也可直接使用 `/leader_set short1 <ID或Binance详情链接>`
或 `/leader_find short1 <名称>`。未找到、
Testnet 币种兼容率不足、短线活跃度不足或方向字段有歧义时，不建立变更确认。

## 上正式盘前

正式盘保持锁定。代码已提供严格分离的生产客户端、`PRODUCTION` 运行模式、生产巡检/审查模式、
独立的 55433 PostgreSQL 数据卷以及 `deploy/systemd/production/` 候选单元。切换不是修改 Testnet URL：

1. 停止测试盘 poller、Telegram、选人和巡检，确认测试盘未决提交已经终态；测试盘数据库只归档，不复制到生产盘。
2. 将专用正式盘 API Key、Secret、数据库密码及根据 `config/copy-production-activation.example.json`
   生成的短时效激活文件放入仓库外 root-only 目录。激活文件必须绑定 API Key 的 SHA-256、
   `https://fapi.binance.com`、150U 边界、Hedge Mode 确认和“不复用测试库”确认。
3. 安装生产候选 systemd 单元并启动独立生产数据库；运行完整迁移。首次绑定前数据库必须没有任何
   测试/交易事实，正式盘账户必须 `canTrade=true`、Hedge Mode、零持仓、零挂单。
